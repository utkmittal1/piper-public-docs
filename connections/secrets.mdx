A secret is a named credential you save in Piper, such as a password, an API key, or a database login. Each secret holds one or more fields, and a field is a short key with a secret value behind it. A database login might be one secret named `Warehouse` with the fields `HOST`, `USERNAME`, and `PASSWORD`. A single API key is a secret with one field.

Piper puts every value in your Mac's keychain and passes it to one command at a time. Piper never shows a stored value back to you.

## When to store a secret

Store a credential as a secret when a task needs to reach something Piper has no integration for, such as your own database, an internal service, or a tool that asks for a token. Where [Integrations](/connections/integrations) already covers the app, set the integration up there instead.

## Where the value is kept

Piper puts each field's value in your Mac's keychain, one keychain item per field, under the service name `Piper`. Piper keeps the secret's name, its description, and the field keys in its own database, and keeps every value out of that database.

Piper has no screen that shows a stored value, and you have no way to ask Piper for a stored value. Once you save a value, the keychain item is the only copy Piper can reach.

<Note>
  Piper stores a secret for you when you add an API key for a model API under **Settings**, then **AI Providers**. It names that secret **BYOM Anthropic**, **BYOM OpenAI**, or **BYOM DeepSeek**, after the provider, and gives it a description naming that provider. The secret appears in your **Secrets** list beside the secrets you wrote, and Piper deletes it when you remove that provider.
</Note>

## Store a credential

<Steps>
  <Step title="Open Secrets">
    In **Settings**, select **Secrets**. Each card in the list shows a secret's name, its description, and how many fields it holds.
  </Step>
  <Step title="Start a new secret">
    Select **New secret**. With nothing stored yet, the button reads **Add your first secret**.
  </Step>
  <Step title="Name it">
    Fill in **Name** with something you will recognize later, like `Warehouse`. **Description** is optional. Write a description anyway. Piper reads the descriptions when it picks the secret a task needs, and a line such as `Snowflake prod, read-only` lets Piper tell that secret apart from the others.
  </Step>
  <Step title="Add the fields">
    Under **Fields**, type a key, like `PASSWORD`, then its value. A key has to start with a letter and use only letters, digits, and underscores, and Piper stores it in capitals. Select **Add field** for each further field. A secret needs at least one field, and Piper sets no ceiling on how many fields a secret holds or how long a value runs.
  </Step>
  <Step title="Save">
    Select **Save secret**. Piper writes every value to the keychain at that moment.
  </Step>
</Steps>

## How Piper uses a secret

Ask for the work in plain words. Piper reads the list of your stored secrets, picks the secret your task needs, and passes its values to the one command that needs them.

From that list, Piper reads names, descriptions, and field keys, never values. Piper passes the values straight into the running command, outside the conversation, so the text Piper writes never holds them. Piper gives that command a time limit and stops it when the limit runs out. A later command in the same task starts without the values.

Before that command's output comes back, Piper looks through it for each value it just passed in and replaces each match with `•••`. A credential the command printed therefore stays out of any chart, file, or reply Piper writes from that output. That replacement is the whole of the protection.

<Note>
  Piper leaves very short values as they are in command output, such as a short code or a short number like a port number. Masking those would blank out ordinary results.
</Note>

When your task needs a credential you haven't stored, Piper's attempt to use the credential fails, and the error names the secret Piper looked for. Piper then tells you which secret is missing and asks you to add it. Add the secret in **Settings**, then **Secrets**, and ask again.

## What Piper does not protect against

Piper's protection is one thing: it keeps a stored value out of your conversation. It shows you no value, it passes values to a command rather than typing them, and it replaces the values that come back in that command's output. The cases below fall outside that protection.

**A command can put the value somewhere Piper does not look.** Piper checks what a command prints back. It does not check what the command writes to a file, and a task can read that file afterwards. It does not check what the command sends over the network either, because Piper leaves the network open so a credential can be used at all.

**The replacement is an exact match.** Piper swaps out the stored value where it appears literally. A command that prints the value encoded, hashed, split across lines, or rewritten into a connection string produces text that does not match, so Piper leaves it as it is.

**Piper never replaces short values.** A very short value, or a short number such as a port number or a PIN, comes back as written.

**Piper checks command output and nothing else.** Piper doesn't check its own replies, the files it writes, or your task's transcript. Piper's instructions tell it never to write a credential into a script, a file, or a reply. The code doesn't enforce that instruction.

**Any task can use any secret you have stored.** Piper offers no way to limit a secret to one project, one task, or one kind of work. Every task can reach every credential in your list.

**A command using a secret can still read and reach anything.** Piper refuses to start such a command unless it runs in the task's own folder, or anywhere in the project's folder for a task in a project. That boundary confines what the command writes. It does not confine what the command reads, and it does not touch the network, so a command holding your credential can read files across your Mac, apart from the folders Piper keeps shut, and send them anywhere. See [The sandbox](/control/sandbox).

**Two kinds of key are handed to the task itself, not to one command.** When you run a task on a model API with your own key, Piper puts that key into the environment the task runs in, so any command the task runs can read it. The same is true of a secret named `byom-web-search`, which is a secret you store yourself and which Piper uses to give that task web search. Neither key goes through the one-command route the rest of this page describes.

**The keychain is your Mac's, not Piper's.** The value sits in your Mac's keychain, so macOS decides what may read it. Piper does not block a task from asking macOS for a keychain value, and Piper's only defense there is an instruction never to reach for a credential any way other than the route on this page. Whether macOS lets a particular request through is macOS's decision, not Piper's.

## Change or remove a secret

Select the pencil on a card to change that secret. You can change the name, the description, and the values, and you can add new fields. You can't edit an existing field's key. The field's value box starts empty, and Piper keeps the stored value unless you type a new value over it.

Select the trash on a card, then **Delete** to confirm. Piper removes the secret's keychain items first and then its own record of it. Piper can't recover the secret after you delete it. If you still need the credential, get a fresh credential from the service.

<Tip>
  Give each secret a name that says what it opens. `Warehouse` and `Stripe live` tell you what you're looking at later. `Key 1` doesn't.
</Tip>
